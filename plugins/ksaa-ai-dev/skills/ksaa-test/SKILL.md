# اختبارات تكشف السلوك الخاطئ

1. اقرأ المواصفة ومعايير القبول وتعليمات المستودع والفحوص الفعلية. حدد طلب المستخدم: خطة، كتابة اختبارات، أم تنفيذها، ولا تتجاوز ذلك.
2. ابن [سلسلة تتبع](../../templates/traceability.md) تربط المتطلب والمعيار وحالة إيجابية وسلبية/حدية والنتيجة المتوقعة والاختبار والبوابة. لا تجعل التوقع نسخة من خوارزمية التنفيذ، ولا تعد `should create` اختبارًا لقواعد العمل.
3. اختر الوحدة والتكامل ورحلة المستخدم والأمان بحسب الحدود المتأثرة. ميّز الاختبار الحقيقي عبر الخدمة أو قاعدة البيانات من mock الوحدة؛ اختبارات الخادم ليست تغطية للمتصفح. راجع عينات [العربية](../../references/language-quality.md) أو [اللعبة](../../references/game-quality.md) إذا دخلت النطاق.
4. تحقق من sandbox والبيانات الاصطناعية وأثر الأمر والنسخة ونسخة البناء/الجهاز/الدور قبل التشغيل. لا تختبر توليد الكود لأول مرة في الإنتاج. عدم وجود أداة أو جهاز ليس نجاحًا.
5. سجل النتيجة الفعلية في [مصفوفة الاختبار](../../templates/test-matrix.md) وفق [بوابات الجودة](../../references/quality-gates.md). عند فشل اختبار، أوقف الانتقال والميزات الجديدة في الجزء المتأثر؛ شخص قرائيًا ثم أصلح فقط ضمن تفويض قائم أو اطلبه وأعد الاختبار.

**المخرج:** حالات وأدلة وعيوب قابلة لإعادة الإنتاج وفجوات صريحة. إنشاء ملف اختبار لا يعني أنه نُفذ، ونجاح اختبارات الوكيل لا يغني عن تقييم بشري لكفايتها.
