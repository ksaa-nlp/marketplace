# تنفيذ محدود ودليل تحقق

1. تحقق من المواصفة ومعايير القبول والنطاق والتفويض والبيئة عبر [دليل السياق](../../references/project-context.md). افحص حالة الملفات وأوامر workspace الفعلية قبل أي تعديل أو تشغيل.
2. نفذ أصغر تغيير مفهوم يحقق المتطلب، مع الحفاظ على عمل المستخدم خارج النطاق وأنماط المشروع وعقوده. عند وجود عميل API مولد، استخدم مولده المحلي المعتمد ولا تعدل ناتجه يدويًا لتخفي انحراف العقد.
3. أضف اختبارات تستند إلى المواصفة وتكشف العيب؛ في لعبة راجع الضغط المكرر والزمن الصفري وإعادة الجولة وتنظيف الموارد، وفي المحتوى راجع صلاحية المورد وحالة النشر إن انطبقت. اقرأ [مصفوفة الألعاب](../../references/game-quality.md) أو [اللغة](../../references/language-quality.md) عند الحاجة فقط.
4. قبل تعديل مخطط بيانات أو ترحيل أو تبعية أو صلاحيات أو معمارية أو إعداد نشر، طبق [بوابات القرار](../../references/decision-gates.md). لا تجعل نجاح الاختبار إذنًا لإجراء غير معتمد.
5. شغّل فحوص النطاق والنسخة والبناء المتأثر وفق [بوابات الجودة](../../references/quality-gates.md). عند الفشل أوقف التقدم: التشخيص القرائي متاح؛ الإصلاح المعدل يتطلب أن يشمله الطلب أو تفويض معالجة موثق، وإلا اطلبه. لا تضعف اختبارًا لتجاوز الفشل.
6. حدّث المواصفة أو الوثائق المتأثرة مع الكود من دون تعديل معيار لإخفاء عيب، أو سجل لماذا لم تتغير. لا تضف تبعية على مهارة تصميم خارج هذه الإضافة؛ اتبع نظام التصميم المحلي إذا كان ضمن الطلب.

**المخرج:** فرق محدود، المتطلب الذي يحققه، ملفات ووثائق، أوامر ونتائج فعلية، المخاطر والمراجعة البشرية المطلوبة. الكود المولد يبقى مسودة حتى مراجعته.
